# Windows 击杀选择与两秒回放算法

2026-09-18 更新：调度已实现。当前执行流程见 [自动录制流程与后台渲染](自动录制流程与后台渲染.md)。本文的算法目标保留，执行细节以当前代码及上述说明为准。

## 1. 本轮确认的窗口

每个可播素材只包含一次选定击杀的前 1 秒和后 1 秒，目标长度 2 秒。Windows 决定录谁，Spark 执行，不使用 LLM 临场决策。

必须分开两个窗口：

- 播出窗口：`[kill_time - 1s, kill_time + 1s]`。
- 内部采集窗口：两侧增加保护量，以覆盖时间估计误差及采集抖动；最终裁成 2 秒，不把保护部分播出。

同一选手的相邻击杀可以共用一次连续原始录制，但每个事件分别导出 2 秒素材。不要沿用上一版“合并后直接播更长连杀片段”的默认行为。两个素材若时间重叠，GUI 标注重复画面，由导播选播，首版不自动把所有素材串播。

若只能获得 GSI 推断时间，2 秒文件长度可以精确，击杀是否恰在中点不能保证。时间字段必须带 `estimated/verified` 和误差范围。严格模式缺少符合约定精度的事件时间时不发布“精确前后各 1 秒”素材，可保留原始录制待定位。精确模式还需游戏事件时间到视频帧的映射，边界按帧量化。

## 2. Windows 端输入

每次击杀候选记录：

```text
event_id、match_id、map_session_id、epoch
killer_steamid64、victim_steamid64（未知允许为空）
event_tick 与 tick_domain（没有则为空）
estimated_kill_time_b：该击杀预计在 B 路呈现的时间
time_uncertainty：估计误差
round_kills_after：本次击杀后的已知本回合击杀数
missed_by_live：主画面没有跟随击杀者的证据，未知则为空
source_quality、manual_pin、identity_mapping
```

`missed_by_live` 只有在 Windows A 路确实代表节目主视角，且有覆盖事件时间的观察者历史时才启用；收到击杀消息时的当前视角不足以证明击杀发生时的主视角。现有单次 GSI 身份接收器不能直接提供该历史。

同一条事件重复收到只更新，不重复计分。GSI 一批快照中击杀数跳增 2，而没有逐次时间证据时，只能生成“密集击杀待定位”候选组，不能编造两次精确击杀时间，也不能凭此获得两个可确定覆盖事件的分数。它可以触发一段探索性原始采集，但需补全定位后才能形成两个精确 2 秒素材。

## 3. 先判断哪些事件能完整录到

在一次规划快照中，对候选统一使用固定保护量 `g`，至少覆盖本快照允许的最大时间误差，并增加实测采集余量。超出允许误差的事件单独标记，不让单个坏样本无限扩大所有窗口。

```text
t_i = estimated_kill_time_b
a_i = t_i - 1 - g          // 必须已经切好镜头且能够采集的时刻
b_i = t_i + 1 + g          // 该目标必须保留到的时刻
```

当前会话暂停、本地事件版本已失效、目标身份不明、命令槽位未确认、时序过期等候选，不进入正式任务计划。

不同选手 i→j 的可连续录制条件：

```text
b_i + setup + transition(i,j) <= a_j
```

`setup` 是设备启动提前量，默认 0.2 秒；`transition` 是额外切换间隔，默认 0。切人后立即启动录制，身份确认在录制中核验，不额外等待稳定。OBS 停启的实际开销仍存在；前条未停止时只允许等到新任务的保护窗口开始，否则报告失败。

同一选手的相邻候选可以保持镜头并连续录制，因此允许窗口重叠。视频处理和回传已与下一次录制解耦，不占用镜头。

## 4. 选择目标：先保证覆盖，再考虑内容

推荐首版采用确定性的字典序优先级，不引入难以解释的综合“精彩分”：

1. **已开始执行或已锁定的任务不抢占。** 不能为了新事件把当前 2 秒片段切坏。
2. **导播手动指定优先。** 只对仍能完整录到、尚未锁定的窗口生效；相互冲突的手动指定必须提示选择，不能悄悄丢弃一个。
3. **最大化完整覆盖的独立击杀数。** 录两次完整击杀优先于只录一次。
4. 覆盖数相同时，优先有可靠证据表明主画面未展示的击杀；未启用此数据源时跳过。
5. 再相同时，优先同回合连续击杀：按每次事件 `min(max(round_kills_after - 1, 0), 4)` 累加；未知记 0。这是可调整的产品选择，并非游戏接口能力。
6. 再相同时，优先切镜头次数少的方案，然后依次以事件时间、SteamID64、event_id 稳定排序。

因此自动方案的目标向量是：

```text
(完整覆盖击杀数, 主画面漏看数, 连杀偏好分, -切镜头次数)
```

按上述顺序比较，不将后面的偏好分用于抵消前面少录一次击杀。对于完全同时、各一杀、没有其他差异的候选，保留当前可用视角；仍相同时用稳定排序，避免网络消息到达顺序决定结果。

## 5. 算法：滚动规划 + 有向无环图最长路径

不要简单“收到一杀立刻下发并锁死”。Windows 利用 A/B 的延迟差，维护 B 路尚未到来的已知事件队列，事件到达或修订、执行反馈、校准变化时重新规划。可设每 50～100 ms 合并一次更新，这是调度节流建议，不是 GSI 数据精度声明。

候选按 `(t_i, SteamID64, event_id)` 排序。固定 `g` 使窗口起止与事件时间同序。

建立边：

- 同一选手 i→j：允许保持同一镜头并连续采集，建立边。
- 不同选手 i→j：仅当 `b_i + setup + transition(i,j) <= a_j` 建立边。
- 虚拟起点代表录制机当前/已锁定任务结束后的状态；只有从该状态来得及完整覆盖的事件才可连入。

每个节点权重为上述目标向量前三项；跨选手的边扣一次切镜头次数。求字典序最大路径，即当前已知候选中的最佳可执行序列。

```text
Plan(events, recorder_state):
    preserve all committed jobs
    candidates = validate_and_deduplicate(events)
    handle feasible manual pins as mandatory reservations
    split remaining timeline around reservations

    for each free time segment:
        sort candidates by (time_b, steamid, event_id)
        # 与左右保留任务也要检查镜头切换及时间边界
        for j in candidates:
            best[j] = unreachable
            if compatible(segment_start_state, j):
                best[j] = score(j) + transition_score(start, j)
            for i before j:
                if best[i] reachable and compatible(i, j):
                    proposal = best[i] + score(j) + transition_score(i, j)
                    retain lexicographically better proposal
        choose best path whose tail fits segment_end_reservation
        backtrack selected events

    coalesce selected same-player raw capture windows
    return versioned provisional plan
```

节点数 n 时单次重规划为 O(n²)，仅针对短期未锁定事件，不扫描全场历史。n 是已知候选事件数量，不是玩家人数。

这是**当前已知事件和固定耗时估计下的最优选择**，不是对尚未到达的未来击杀作保证。若时间误差或执行耗时模型变化，未锁定区间重新计算。

同一选手连续段可共用原始录制；不能因为分成多个 2 秒输出文件就假定它们需要多个同时工作的 CS2 实例。反过来，不同选手的冲突窗口不能通过 OBS 多开录制解决，因为源画面只有一个视角。

## 6. 计划何时锁定

Windows 先展示可调整的暂定计划，接近执行时刻才提交，充分利用延迟差收集附近后续事件。

```text
latest_dispatch_i = a_i
                    - setup_from_current_state
                    - control_transport_budget
                    - safety_margin
```

这里 `setup_from_current_state` 包含尚未完成的切镜头/身份确认/录制启动。正在连续录同一选手时可以更小，但不能重复扣除已在 transition 中执行完的工作。

到提交时刻重新核验，发送含 `plan_revision/job_id/epoch` 的任务，发送时自动转换为 Linux 本地 epoch，Linux 确认后加入无冲突录制队列。发送结果不确定时按 job_id 查询，不把旧任务当成已经取消。录制机拒绝迟到命令并返回原因。

已经提交但尚未执行的任务，若要替换，必须经过取消确认且新任务仍有足够提前量；默认不做此类抢占。手动“强制切换”如果另行提供，应明确会废弃当前片段，不属于首版默认录制算法。

两路最小时间差预算加入收集候选的等待时间 W：

```text
Δ >= L_detect + W + L_control + setup + 1s + g + M
```

Δ 可调，推荐根据实测选择满足预算的最小稳定值；无需为了 2 秒素材固定等待 20 秒。延迟差越大，能看到更多未来候选，但回放就绪也更晚。

## 7. 冲突案例

以下 t 是统一比赛时间或校准后的同域时间；候选都在提交截止前已知。算例统一 `g=0.2s`、不同视角转换耗时 `0.3s`，不是本机实测值。

| 候选 | 目标回放窗口 | 原始采集保护窗口 |
|---|---|---|
| A 在 10.0 秒击杀 | 9.0～11.0 | 8.8～11.2 |
| B 在 10.2 秒击杀 | 9.2～11.2 | 9.0～11.4 |
| B 在 10.7 秒再次击杀 | 9.7～11.7 | 9.5～11.9 |

选择 B：同一个 B 视角可以覆盖两个事件，A 只能覆盖一个。原始素材连续录 B 的 9.0～11.9 秒，最后分别导出 B 的两段 2 秒素材。A 标记“视角冲突未录”，不伪称可以稍后排队补上。

其他边界：

- A 在 10.0 秒、B 在 12.1 秒：即使两个 2 秒播出窗口不重叠，也因保护量和切人耗时不能都录。
- A 在 10.0 秒、B 在 13.0 秒：`11.2 + 0.3 <= 11.8`，理论上可以连续录两人。
- A 已经锁定执行才收到 B 的双杀：保持 A；B 标记与已承诺窗口冲突，不追求事后最优而破坏在录片段。
- A/B 完全同时各一杀：手动指定优先；否则按漏看证据、连杀偏好、当前视角、稳定排序决策。
- GSI 同批显示 B 击杀数 +2，但两个时刻未知：不会假设它们都发生于 10.2 秒；等待精确源补全，或只生成标为近似的待定位原始素材。

## 8. Windows 导播台与验收

每条事件显示：预计时刻、录制目标、时间精度、暂定/锁定/录制/可播状态，以及选择理由。未录制原因至少区分 `conflict`、`missed_deadline`、`uncertain_time`、`identity_unknown`。

录制选择与播出选择是两步：算法决定有限录制资源优先给谁；导播在已回传的 2 秒素材中决定实际播谁。自动录到的素材不得自行抢占 Windows OBS 节目。

实现时必须验证：同时间多事件、同人双杀、不同人窗口接近、手动锁定冲突、已提交任务不可抢占、消息重复、事件修订、断线重连、回档换图、身份变化、时间误差超限。严格精确模式要求有事件—视频定位证据；没有此证据不能只检查文件时长 2 秒便宣称验收通过。
