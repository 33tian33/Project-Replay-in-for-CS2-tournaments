# 道具击杀追踪

已实现 `replay-source` Demo/CSTV 解析器和 `tracking_mode=native` 原生 NetCon 镜头后端。2026-09-17 已用真实 CS2 + OBS 验证 HE 跟随与火区定位、实际镜头回读和两秒素材产出。启动方式与验证边界见 [原生自动追雷交付与验证](原生自动追雷交付与验证.md)。以下保留通用事件模型及外部 bridge 协议。

使用解析器时配置 `event_source=parser`，GSI 仍提供会话和观战信息，但不再重复创建来源未知的击杀候选。GSI 差分不能可靠识别雷杀。

## 事件与调度

通过现有 `POST /api/events` 提交事件，在原字段外添加：

```json
{
  "utility": {
    "kind": "hegrenade",
    "id": "epoch1-round7-A-throw3",
    "evidence": "事件适配器记录：投掷记录 throw3 与死亡事件 death8 关联"
  }
}
```

这是新增字段示例，提交时仍需提供原有 `player`、`time` 等必要字段。`player` 保留击杀归属，`time` 是 B 路预计击杀时间（毫秒）。`utility` 缺省表示沿用选手视角；已知是道具击杀、但关联未完成时，可以提交仅含 `kind` 的对象，显示 `TRACKING_UNRESOLVED`，不会退回投掷者视角。

类型支持 `hegrenade`、`molotov`、`incgrenade`、`flashbang`、`smokegrenade`、`decoy`。后三类仅在明确存在对应道具伤害击杀时使用。实例 ID 必须由数据适配器生成，在比赛、地图和 epoch 内唯一，并能在 A/B 两路解析到同一次投掷；不能直接复制某一路实体索引。关联证据是来源记录，不等于本程序独立验证了游戏事实。

同一投掷者的不同道具、枪杀和道具击杀分别占用镜头。只有同一实例、同一类型、同一投掷者、同一会话的事件可以共用镜头；单次任务最长仍为 30 秒。每个击杀分别输出前后各一秒。适配器负责确认整个任务窗口都能用同一镜头策略覆盖，包括燃烧范围内的多杀；不能覆盖时必须拒绝准备任务或报告验证失败。

## 外部 bridge 镜头适配器协议 v1

在实际录制的 Worker 设置 `tracking_url`。本机录制直接使用本机配置；远程录制由远程 Worker 的配置决定，无需配置 token。现有 `setup` 是全部镜头准备和 OBS 启动预算，应按实测耗时配置。严格定位模式仍会阻止实时出片，镜头验证没有解决击杀与视频帧的时间对齐问题。

适配器须单独实现以下接口，建议与 Worker 同机运行。请求不携带配对 token；HTTP 重定向不会跟随。

### PUT /v1/tracking/{job_id}

请求体为完整 `Job`，含 `utility`、投掷者 `player`、比赛/地图/epoch、`events` 和 Worker 时钟下的 `start/end`。成功返回 2xx。

适配器应：

1. 幂等地持有此任务镜头；拒绝同 ID 不同内容、错误会话和资源冲突。
2. 将跨路道具实例映射到 B 路实体；需要时使用投掷时刻、投掷者、轨迹等源记录。不得把 A 路实体索引直接当作 B 路实体。
3. 飞行时追踪道具；爆炸后保持作用区域；燃烧道具已经落地时可以直接从火区开始。
4. 从实际游戏镜头状态产生独立验证证据。仅发出了控制命令或仍观察着投掷者，不能视为验证成功。
5. 设置租约，在 `end` 后自动释放，以处理 Worker 崩溃或释放请求丢失。

### GET /v1/tracking/{job_id}

返回示例：

```json
{
  "job_id": "capture-job-id",
  "epoch": 1,
  "utility_id": "epoch1-round7-A-throw3",
  "phase": "projectile",
  "observed_at": 1789600000000,
  "camera_verified": true,
  "evidence": "B 路实体句柄及镜头目标的独立采样记录"
}
```

`observed_at` 必须是 **Worker 同一时钟域下的实际采样时间**，不能在响应时给旧样本刷新时间。样本最多允许滞后 500ms，不接受未来时间。异机适配器必须自行完成时钟映射。

阶段只允许 `projectile`（飞行道具）和 `effect`（爆炸或燃烧作用区域），允许直接从 `effect` 开始；转入 `effect` 后不能回到 `projectile`。实体因爆炸消失时应更新为经过验证的作用区域镜头；丢失目标、遮挡导致无法确认、自动导播抢镜等情况返回 `camera_verified: false`，不得继续复用旧的成功状态。

Worker 在准备期限内轮询确认，录制期间持续采样检查。错误任务/道具/epoch、过期证据、空证据、非法阶段或连接中断会使采集失败。现有检查属于采样验证，不保证采样间每帧均正确。

### DELETE /v1/tracking/{job_id}

幂等释放此任务持有的镜头，成功返回 2xx；未知或已释放任务也应成功。不得释放其他任务的镜头。Worker 在正常录制结束、失败或取消时调用；即使 PUT 应答丢失也会尝试释放。释放未确认时暂停后续采集，并记录告警。

## 素材与界面

事件界面显示道具种类、实例及追踪不可用/关联待确认状态；手动添加事件可以填写道具信息。素材保留 `utility`、`camera_quality`、`camera_evidence`。真实录制标为 `sampled`，每个镜头阶段保留首尾样本，整个任务最多四条；这些是任务级证据，不是逐帧证明。演示素材标为 `demo`，不产生真实镜头证据。

## 验证边界

自动测试覆盖镜头冲突、同一道具多杀、缺失关联、无适配器、远程目标不一致、准备/监测/释放协议、过期或错误反馈、飞行转作用区域和阶段回退。bridge 协议通过模拟 HTTP 验证；native 后端另有真实 CS2 Demo + OBS 验证，不能将此视为真实在线 GOTV 验收。

native 后端无需另写 bridge 服务；在线接入仍需真实事件源、B 路观战连接和时钟校准。验收样本至少覆盖多人同时投雷、同一人多次投掷、投掷者死亡后击杀、燃烧多杀、实体消失、镜头抢占和 A/B 延迟变化。
